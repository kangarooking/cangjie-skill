# 阶段 0.5 — 可蒸性预筛选 (Pre-filter)

## 为什么必须有这一步

**不是所有书都值得蒸馏。** 小说、散文、金句集 — 蒸出来质量有限,还烧掉几万 token 和 30-90 分钟。开工前先用 5 分钟判断"这本书值不值得蒸",比跑完整个流水线再发现"没东西可蒸"划算得多。

> 引用 (随风《蒸馏读书法》): "最适合的是方法论密度高的书:有清晰的框架、可复用的原则、能拆成步骤。"

## 可蒸性三问 (5 分钟内回答)

对一本书 (或视频/播客/课程),问三个问题:

1. **框架密度**: 书里有没有作者反复使用、起了名字的框架/模型/流程? (如"PSF三关检验""MVD最小可行部署")
2. **原则可复用性**: 能否把原则拆成跨场景复用的规则,而不是只适用于书中那个故事?
3. **步骤可拆性**: 能不能拆成 1-2-3 可执行步骤,让 agent 照着做?

**三问全过 → 值得蒸,进入阶段 0。**
**两过一不过 → 可以蒸,但提前告知用户预期 (数量会偏少)。**
**≤1 问通过 → 不值得蒸,降级处理:**

- 直接给用户一份摘要/DIGEST,不做 skill
- 明确告知: "这本书方法论密度低,蒸馏成 skill 的价值有限,建议只做精华笔记"
- 把判断结果写进 PIPELINE_STATE.md,留档

## 先查复用 (Pre-filter 第一动作)

**同一本书不需要每个人蒸馏一遍。** 开始前先搜索是否已有现成蒸馏产物:

1. 搜 GitHub: `kangarooking/cangjie-skill` 社区仓库、ClawHub、`<书名> + skill 蒸馏`
2. 搜已安装 skills: `skills_list` 看有没有同名/同主题 skill
3. 已有产物 → 直接安装复用,把链接给用户,跳过整个流水线
4. 没有 → 继续自蒸

## 成本预期 (开工前告知用户)

| 内容体量 | 预计时长 | 预计 token |
|---|---|---|
| 短视频 (<10K 字符) | 10-20 分钟 | 数千 |
| 一本书 (20 万字) | 30-90 分钟 | 数万 ~ 十余万 |

开工前把预期告知用户,让用户决定值不值得蒸。
